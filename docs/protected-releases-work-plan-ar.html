1. الملخص التنفيذي

الهدف هو إنتاج نسختين محميتين من التطبيق الحالي تعملان Offline عند الحاجة، مع ربط الترخيص بالجهاز ومنع تشغيل النسخة المحمية قبل نجاح التحقق. سيتم استخدام تشويش الكود كطبقة ردع، لكن الاعتماد الأمني الأساسي سيكون على توقيع رقمي بمفتاح خاص لا يغادر بيئة الإصدار.

Android قابل للتنفيذ بدرجة عالية؛ المشروع يستخدم Capacitor ولديه مسار Offline ومشروع Android جاهز.
Windows قابل للتنفيذ؛ يتطلب غلاف Electron، تشغيل API محلي، ودمج وضع PGlite المكتبي.
الترخيص ملف موقّع يحتوي المنصة ومعرّف الجهاز والإصدار والصلاحيات وتاريخ الانتهاء الاختياري.
البيانات حماية مستقلة لقاعدة البيانات والنسخ الاحتياطية، لأن الترخيص وحده لا يشفر البيانات.
حدود واقعية: لا توجد حماية Offline تمنع الهندسة العكسية بشكل مطلق. الهدف هو منع النسخ العادي، كشف العبث، ورفع تكلفة التعديل، مع حماية صحيحة للمفاتيح والبيانات.

2. النطاق وما هو خارج النطاق

داخل النطاقخارج النطاق في هذه الخطة
نسخة Android محمية ونسخة Windows محمية من نفس المصدر.إعادة تصميم وظائف المستودع أو تغيير قواعد العمل.
نظام ترخيص Offline موقّع وربط الترخيص بالجهاز.بوابة تجارية كاملة لإدارة العملاء والفوترة.
تشويش ملفات الإنتاج وتوقيع APK وEXE.ضمان منع جميع أشكال فك الحزم والهندسة العكسية.
حماية التخزين المحلي والنسخ الاحتياطية حسب قرار المرحلة 2.تغيير قاعدة بيانات الإنتاج أو ترحيل بيانات حقيقية دون موافقة منفصلة.
اختبار وتوثيق كل مرحلة داخل هذا المشروع.رفع إصدارات نهائية للعملاء قبل اعتماد بوابة التسليم.

3. التصميم الأمني المعتمد

3.1 الترخيص الموقّع

  1. توليد زوج مفاتيح Ed25519 أو RSA-3072 خارج المستودع.
  2. حفظ المفتاح الخاص في جهاز/مخزن إصدار محمي، وإدخال المفتاح العام فقط ضمن التطبيق.
  3. إنشاء ملف ترخيص يحتوي: المنتج، المنصة، معرّف الجهاز، رقم الترخيص، الإصدار، الصلاحيات، تاريخ الإصدار والانتهاء.
  4. توقيع الحمولة بالمفتاح الخاص.
  5. تحقق التطبيق من التوقيع، المنصة، الجهاز، الإصدار، وحالة الانتهاء قبل فتح الوظائف.

3.2 معرّف الجهاز

المنصةالمصدر المقترحسياسة التغيير
Windowsمعرّف مركب من مصادر عتاد متعددة مع fallback واضح، دون الاعتماد على WMIC وحده.إعادة تفعيل عند تغيير عتاد جوهري؛ دعم إصدار إعادة تفعيل يدوي.
Androidمعرّف تثبيت ثابت أو معرف نظام مناسب عبر Plugin Native، مع توثيق أثر حذف البيانات وإعادة الضبط.إعادة تفعيل عند فقدان المعرّف أو إعادة ضبط المصنع حسب السياسة المعتمدة.

3.3 طبقات الحماية

  1. توقيع الترخيص: الحاجز الأمني الأساسي.
  2. تشويش JavaScript وملفات الخادم المحلية: تقليل سهولة القراءة.
  3. تحقق Native حيث يكون عملياً: رفع تكلفة تعطيل الفحص.
  4. توقيع APK وEXE: إثبات المصدر وكشف الاستبدال والعبث.
  5. تشفير التخزين والنسخ الاحتياطية: حماية البيانات، وهو هدف منفصل عن الترخيص.

4. خطة المراحل التنفيذية

لا تنتقل أي مرحلة إلى التالية إلا بعد إغلاق اختبارها وتسليم توثيقها. كل مرحلة تنتج مخرجاً قابلاً للمراجعة وسجلاً للقرارات والنتائج.

المرحلة 0 — اعتماد المتطلبات وخط الأساس

الهدف: تثبيت النطاق ومنع البدء بتصميم غير معتمد

الأعمال

  • اعتماد الفرق بين النسخة العادية والمحمية.
  • تحديد Offline/Online وسياسة انتهاء الترخيص وإعادة التفعيل.
  • حصر المنصات: Windows 10/11 x64 وAndroid 8+ أو الحد الأدنى المعتمد.
  • تثبيت قرار Ed25519 أو RSA، وقرار تشفير البيانات المحلية.
الاختبار ومعيار النجاح: توقيع محضر متطلبات يتضمن المنصات، نموذج الترخيص، حالات الرفض، وسياسة فقدان الجهاز. لا توجد بنود مفتوحة تمنع تصميم المرحلة التالية.
التوثيق الناتج: وثيقة المتطلبات المعتمدة، قاموس حالات الترخيص، قائمة قرارات مفتوحة، ومصفوفة قبول أولية.

المرحلة 1 — تدقيق البنية وتجهيز فروع البناء

الهدف: فصل البناء العادي عن المحمي دون تغيير الوظائف

الأعمال

  • تثبيت baseline من المشروع الحالي واختبارات البناء الحالية.
  • تحديد نقطة دخول Windows، ومسار Capacitor Android، ووضع PGlite/Offline.
  • تصميم بنية مشتركة لـ License Core مع محولات Windows وAndroid.
  • إضافة تعريفات بناء واضحة: standard وprotected مع منع اختلاط ملفات الأسرار.
الاختبار: تشغيل build وtypecheck للنسخة الحالية، تشغيل الويب وAPI، إنشاء نسخة Android غير محمية، والتحقق من أن baseline لا يحتوي ملفات مفاتيح أو keystore.
التوثيق: مخطط البنية، خريطة نقاط الدخول، جدول المتغيرات، سياسة الفروع/الإصدارات، وسجل baseline مع commit.

المرحلة 2 — تصميم وإدارة المفاتيح والترخيص

الهدف: بناء أساس أمني لا يعتمد على سر داخل التطبيق

الأعمال

  • إنشاء زوج مفاتيح توقيع خارج Git.
  • تعريف مخطط License Payload وإصداراته.
  • إنشاء أداة إصدار داخلية لا تُضمّن في حزم العملاء.
  • تحديد حفظ ملف الترخيص، النسخ الاحتياطي، الإبطال، والانتهاء.
  • تحديد سياسة تدوير المفتاح وإصدار key-id للمستقبل.
الاختبار: ترخيص صحيح يقبل، ترخيص معدّل يرفض، توقيع بمفتاح مختلف يرفض، ترخيص لمنصة أخرى يرفض، ترخيص لجهاز آخر يرفض، وملف منتهي يرفض حسب السياسة.
التوثيق: مواصفة الترخيص، سياسة إدارة المفاتيح، إجراء إصدار/إلغاء الترخيص، سجل ملكية المفاتيح، وأمثلة غير حساسة للاختبار. لا يوثق الملف المفتاح الخاص نفسه.
بوابة أمنية: لا تبدأ مراحل دمج الحماية إذا كان المفتاح الخاص أو كلمات مرور التوقيع موجودة في المستودع أو ضمن ملفات البناء.

المرحلة 3 — طبقة الترخيص المشتركة

الهدف: توحيد التحقق ومنع اختلاف منطق Windows وAndroid

الأعمال

  • تنفيذ parser وvalidator للحمولة والتوقيع.
  • تعريف نتائج موحدة: checking، valid، missing، invalid، expired، device-mismatch، tampered.
  • تطبيق مقارنة ثابتة وآمنة حيث يلزم.
  • إضافة versioning وkey-id دون تخزين أسرار في الكود.
  • فصل واجهة الترخيص عن واجهة التطبيق الأساسية.
الاختبار: اختبارات وحدات لكل حقول الترخيص، fuzz للحمولة غير الصحيحة، اختبار Unicode/المسافات، اختبار الساعة غير الصحيحة ضمن حدود السياسة، واختبار عدم فتح الوظائف عند أي فشل.
التوثيق: عقد License Core، جدول حالات الخطأ، مخطط تدفق التحقق، واختبارات موثقة مع نتائجها.

المرحلة 4 — تطبيق Android المحمي

الهدف: حماية APK مع الحفاظ على Offline والمزامنة

الأعمال

  • إضافة شاشة تفعيل RTL تعرض معرف الجهاز وتدعم النسخ.
  • منع تحميل App الرئيسي قبل اكتمال التحقق.
  • ربط معرف Android بسياسة إعادة التفعيل.
  • تشويش Bundle الإنتاج مع استثناء الملفات التي تتأثر وظيفياً بعد اختبارها.
  • توقيع APK من keystore خارج المستودع، وتثبيت سر التوقيع عبر بيئة إصدار آمنة.
الاختبار: تثبيت جديد، تفعيل صحيح، مفتاح خاطئ، ترخيص لجهاز آخر، حذف ملف الترخيص، حذف بيانات التطبيق، إعادة تشغيل Offline، استعادة نسخة احتياطية، تحديث APK مع بقاء التفعيل، والتحقق من توقيع APK.
التوثيق: دليل بناء APK، دليل التفعيل للمستخدم، سياسة إعادة التفعيل، سجل fingerprint للتوقيع، ومصفوفة توافق إصدارات Android.
قرار مطلوب: هل يؤدي حذف بيانات التطبيق إلى طلب ترخيص جديد، أم توجد آلية استعادة مرخصة؟ يجب اعتماد ذلك قبل الإطلاق.

المرحلة 5 — غلاف Windows المحمي

الهدف: إنتاج تطبيق Windows محلي يعمل دون PostgreSQL خارجي

الأعمال

  • إنشاء/اعتماد Electron wrapper متوافق مع بنية API والواجهة الحالية.
  • تشغيل الخادم المحلي بوضع DAMASCUS_DESKTOP=1 ومسار بيانات ثابت وآمن.
  • تضمين مخطط PGlite المطلوب والتحقق من جاهزية قاعدة البيانات.
  • عرض شاشة تحميل وتفعيل قبل فتح الواجهة.
  • تحديد معرّف Windows متعدد المصادر مع fallback قابل للتشخيص.
  • تشويش ملفات renderer وserver وElectron الضرورية.
الاختبار: بناء وتشغيل على Windows 10 و11 x64، تشغيل أول مرة، إنشاء قاعدة محلية، تفعيل ورفض، نسخ البرنامج لجهاز آخر، إعادة تشغيل، إغلاق قسري، حفظ البيانات، ترقية الإصدار، واستعادة النسخة الاحتياطية.
التوثيق: دليل تثبيت Windows، دليل تشغيل Portable/Installer، مسار البيانات، إجراء التشخيص، سياسة تغيير العتاد، وسجل توافق Electron/Node.
شرط الإصدار: يجب توقيع EXE/Installer رقمياً إن كان التوزيع خارجياً. النسخة غير الموقعة قد تعمل لكنها ليست معيار تسليم احترافي.

المرحلة 6 — تشفير البيانات المحلية والنسخ الاحتياطية

الهدف: حماية محتوى المستودع، وهو هدف مستقل عن ترخيص التطبيق

الأعمال

  • اختيار طبقة تشفير مناسبة لـ PGlite/IndexedDB أو طبقة ملفات/حقول بحسب القيود.
  • حماية مفاتيح Android عبر Android Keystore.
  • حماية مفاتيح Windows عبر DPAPI أو مخزن نظام مناسب.
  • تشفير حزم النسخ الاحتياطية مع nonce وauthentication tag وإدارة إصدارات.
  • منع تسجيل الأسرار والبيانات الحساسة في السجلات.
الاختبار: قراءة ملف قاعدة البيانات الخام، محاولة تعديل سجل مشفر، استعادة حزمة بكلمة/مفتاح خاطئ، كشف العبث، فقدان مفتاح الجهاز، تصدير واستيراد، واختبار سلامة البيانات بعد التشفير.
التوثيق: تصميم تشفير البيانات، دورة حياة المفاتيح، سياسة فقدان المفتاح، توافق النسخ، وإجراء استعادة آمن للمشرف.
تنبيه: لا يُعلن أن البيانات «مشفرة» قبل نجاح اختبار قراءة الملفات الخام والتأكد من عدم وجود مفاتيح فك ثابتة داخل JavaScript.

المرحلة 7 — خطا البناء والإصدار المحمي

الهدف: جعل بناء النسخ قابلاً للتكرار وغير قابل لتسريب الأسرار

الأعمال

  • تعريف أوامر منفصلة: standard وprotected لكل منصة.
  • تثبيت الاعتماديات بقفلها والتحقق من checksum عند الإمكان.
  • إخراج artifacts خارج شجرة المصدر الحساسة.
  • منع تضمين generator وأي ملف توقيع أو سجل عملاء في الحزمة.
  • توليد manifest وchecksum لكل إصدار.
الاختبار: بناء نظيف من checkout جديد، بناء متكرر يعطي نفس المحتوى المتوقع باستثناء القيم الزمنية المعروفة، فحص الحزمة بحثاً عن private key/secret/generator، والتحقق من checksum والتوقيع.
التوثيق: Runbook للإصدار، متطلبات البيئة، قائمة المدخلات، قائمة مخرجات كل منصة، سياسة الاحتفاظ بالإصدارات، وسجل checksum.

المرحلة 8 — اختبار القبول والأمن والتوافق

الهدف: إثبات أن النسخ المحمية تعمل ولا تفتح عند العبث

الأعمال

  • اختبار وظيفي كامل للمواد والحركات والتقارير والنسخ الاحتياطية والمزامنة.
  • اختبار مصفوفة الأجهزة والإصدارات.
  • مراجعة الحزمة وفكها وتحليل وجود معلومات حساسة.
  • اختبار تحديث النسخة المحمية والعودة الآمنة عند الفشل.
  • تسجيل كل العيوب وتصنيفها قبل التسليم.
معيار النجاح: لا توجد أخطاء حرجة أو عالية مفتوحة؛ جميع حالات الترخيص الأساسية ناجحة؛ البيانات لا تفقد بعد الإغلاق/التحديث؛ توقيع الحزم صالح؛ وفحوص الأسرار نظيفة.
التوثيق: تقرير اختبار شامل، مصفوفة جهاز/إصدار، تقرير أمن مختصر، قائمة العيوب، وقرار Go/No-Go موقع.

المرحلة 9 — التسليم والتشغيل والدعم

الهدف: تسليم قابل للتكرار مع إجراءات واضحة بعد الإطلاق

الأعمال

  • إعداد حزمة العميل: التطبيق فقط، دليل التثبيت، ودليل التفعيل.
  • إعداد حزمة المورد السرية خارج التوزيع: أداة الإصدار وإجراءات المفاتيح.
  • تحديد قناة استلام Device ID وتسليم الترخيص دون نشر أسرار.
  • تعريف إجراءات التحديث، الإبطال، الاستبدال، وفقدان الجهاز.
  • إنشاء نموذج بلاغات يتضمن المنصة والإصدار ومعرّف الترخيص دون البيانات الحساسة.
الاختبار: تجربة تسليم كاملة لمستخدم جديد، تفعيل من الصفر، تحديث، استعادة، دعم جهاز جديد، وتشغيل إجراء الطوارئ عند فقدان المفتاح.
التوثيق: دليل المستخدم، دليل المورد، نموذج تسليم، سجل الإصدارات، إجراء الطوارئ، وسياسة الدعم والاحتفاظ بالسجلات.

7. بوابات القرار قبل التنفيذ

  • اعتماد خوارزمية التوقيع: Ed25519 أو RSA-3072.
  • اعتماد سياسة انتهاء الترخيص والإبطال وإعادة التفعيل.
  • اعتماد ما إذا كانت قاعدة البيانات والنسخ الاحتياطية ستُشفّر في الإصدار الأول.
  • توفير بيئة إصدار آمنة ومخزن أسرار للـ private key وAndroid keystore.
  • اعتماد Windows target: Portable ZIP أو Installer موقّع.
  • اعتماد الحد الأدنى لإصدارات Windows وAndroid والأجهزة المدعومة.
  • تعيين مالك إصدار المفاتيح ومالك اعتماد الإصدارات.
  • الموافقة الصريحة على بدء التنفيذ بعد مراجعة هذه الوثيقة.

8. المخرجات النهائية المتوقعة

Android Protected APK حزمة موقعة، مشوشة، قابلة للتفعيل، مع checksum ودليل تثبيت.
Windows Protected Package Portable أو Installer موقّع، مع بيانات محلية وحارس ترخيص.
Vendor License Kit أداة إصدار وإجراءات داخلية خارج حزمة العميل والمستودع العام.
Documentation Set أدلة البناء، التفعيل، التحديث، الاستعادة، الدعم، وتقارير الاختبار.

9. معيار الإطلاق Go/No-Go

Go فقط عند تحقق جميع الشروط التالية:

  • نجاح اختبارات الترخيص والتوقيع على المنصتين.
  • عدم وجود private key أو keystore أو كلمات مرور في Git أو الحزم.
  • نجاح اختبار تحديث واستعادة البيانات.
  • اكتمال توثيق البناء والتفعيل والدعم.
  • مراجعة أمنية للحزمة النهائية وإغلاق العيوب الحرجة والعالية.
  • اعتماد المالك النهائي للإصدار وسجل checksum والتوقيع.
قرار المراجعة: هذه الوثيقة خطة وليست موافقة تنفيذ. يبدأ العمل البرمجي فقط بعد اعتماد القرارات الواردة في القسم 7 وتحديد أي تغييرات مطلوبة على الخطة.
