             نظام مستودع الإسعاف والطوارئ — دمشق
       خطة عمل إنشاء النسخ المحمية لـ Windows و Android
===============================================================================

الحالة       : للمراجعة والاعتماد قبل التنفيذ
الإصدار      : 1.0
تاريخ الإعداد: 22 أغسطس 2026
النطاق       : نسخة Windows محمية + نسخة Android محمية
النهج        : ترخيص رقمي موقّع + تشويش الكود + توقيع الحزم + حماية التخزين

هذه الوثيقة خطة تنفيذية فقط. لم يتم بموجبها تعديل كود التطبيق أو إنشاء
نسخ إنتاجية أو تغيير قاعدة البيانات.

-------------------------------------------------------------------------------
1. الملخص التنفيذي
-------------------------------------------------------------------------------

الهدف هو إنتاج نسختين محميتين من التطبيق الحالي تعملان Offline عند الحاجة،
مع ربط الترخيص بالجهاز ومنع تشغيل النسخة المحمية قبل نجاح التحقق.

سيتم استخدام تشويش الكود كطبقة ردع، لكن أساس حماية الترخيص سيكون توقيعاً
رقمياً بمفتاح خاص لا يدخل المستودع ولا حزمة التطبيق.

التقييم:

  - إمكانية تطبيق الحماية على Android : عالية جداً.
  - إمكانية تطبيق الحماية على Windows : عالية، مع الحاجة إلى غلاف Electron.
  - منع النسخ البسيط بين الأجهزة     : جيد.
  - مقاومة الهندسة العكسية           : محدودة ولا يمكن ضمانها بشكل مطلق.
  - حماية البيانات المحلية            : تحتاج طبقة مستقلة عن الترخيص.

القاعدة الأمنية الأساسية:

  لا يتم وضع أي private key أو Android keystore أو كلمة مرور توقيع داخل Git
  أو داخل ملفات التطبيق أو داخل حزمة العميل.

-------------------------------------------------------------------------------
2. النطاق
-------------------------------------------------------------------------------

داخل النطاق:

  1. إصدار نسخة Android محمية ونسخة Windows محمية من نفس المصدر.
  2. إنشاء ترخيص Offline موقّع مرتبط بالجهاز.
  3. إضافة شاشة تفعيل وحارس تشغيل قبل فتح التطبيق.
  4. تشويش ملفات الإنتاج.
  5. توقيع APK و EXE أو Installer.
  6. دراسة وتنفيذ حماية البيانات المحلية والنسخ الاحتياطية.
  7. اختبار وتوثيق كل مرحلة داخل هذه الخطة.
  8. إعداد إجراءات البناء والتسليم والدعم.

خارج النطاق في هذه الخطة:

  1. إعادة تصميم وظائف المستودع أو قواعد العمل.
  2. إنشاء بوابة تجارية كاملة للعملاء والفوترة.
  3. ضمان منع جميع أشكال فك الحزم والهندسة العكسية.
  4. تغيير قاعدة بيانات الإنتاج دون موافقة منفصلة.
  5. تسليم إصدارات للعملاء قبل اعتماد الاختبارات النهائية.

-------------------------------------------------------------------------------
3. التصميم الأمني المقترح
-------------------------------------------------------------------------------

3.1 الترخيص الموقّع

يتم إنشاء زوج مفاتيح غير متماثل:

  - Private Key : يبقى لدى مالك النظام فقط، خارج Git وخارج التطبيق.
  - Public Key  : يضمّن داخل التطبيق للتحقق فقط.

تحتوي حمولة الترخيص على:

  - اسم المنتج.
  - المنصة: Windows أو Android.
  - معرّف الجهاز.
  - رقم الترخيص.
  - إصدار الترخيص.
  - تاريخ الإصدار.
  - تاريخ الانتهاء، إن تم اعتماد التراخيص المؤقتة.
  - الصلاحيات أو الوحدات المسموح بها.
  - رقم إصدار التطبيق المتوافق.

يتم توقيع الحمولة بالمفتاح الخاص. ويتحقق التطبيق من:

  1. صحة التوقيع.
  2. تطابق المنصة.
  3. تطابق معرّف الجهاز.
  4. توافق إصدار التطبيق.
  5. تاريخ الصلاحية.
  6. سلامة ملف الترخيص وعدم العبث به.

الخيار المقترح: Ed25519، أو RSA-3072 إذا فرضت بيئة التشغيل ذلك.

3.2 معرّف الجهاز

Windows:

  - استخدام أكثر من مصدر عتاد.
  - عدم الاعتماد على WMIC وحده.
  - وجود fallback واضح وقابل للتشخيص.
  - إعادة التفعيل عند تغيير عتاد جوهري وفق سياسة معتمدة.

Android:

  - استخدام معرف نظام أو معرف تثبيت عبر طبقة Native مناسبة.
  - توثيق أثر حذف بيانات التطبيق وإعادة تثبيته وإعادة ضبط المصنع.
  - تحديد سياسة واضحة عند فقدان المعرّف.

3.3 طبقات الحماية

  1. التوقيع الرقمي للترخيص: طبقة الحماية الأساسية.
  2. تشويش JavaScript وملفات الخادم المحلية: تقليل سهولة القراءة.
  3. تحقق Native حيث يكون عملياً: رفع تكلفة تعطيل الحماية.
  4. توقيع APK و EXE: إثبات المصدر وكشف الاستبدال.
  5. تشفير البيانات والنسخ الاحتياطية: حماية المحتوى، وهو هدف مستقل.

6. المخاطر وخطط المعالجة
-------------------------------------------------------------------------------

الخطر: تسريب المفتاح الخاص
الأثر: إصدار تراخيص غير مصرح بها.
المعالجة: إخراجه من Git، استخدام مخزن أسرار، صلاحيات محدودة، وتدوير المفتاح.
الأولوية: عالية.

الخطر: تسريب Android keystore
الأثر: توقيع نسخ مزيفة أو تحديثات غير موثوقة.
المعالجة: حفظه خارج المستودع، نسخة احتياطية مشفرة، وعدم وضع كلمات المرور
          داخل السكربتات.
الأولوية: عالية.

الخطر: معرّف جهاز غير ثابت.
الأثر: طلب إعادة تفعيل غير متوقع.
المعالجة: مصادر متعددة، سياسة إعادة تفعيل، وأداة دعم.
الأولوية: متوسطة.

الخطر: فقد مفتاح تشفير البيانات.
الأثر: عدم القدرة على قراءة البيانات.
المعالجة: سياسة استرداد مدروسة ونسخة احتياطية مشفرة للمفاتيح.
الأولوية: عالية.

الخطر: فشل التشويش وظيفياً.
الأثر: تعطل التطبيق أو نقص التقارير.
المعالجة: استثناءات محدودة واختبار كامل بعد التشويش.
الأولوية: متوسطة.

الخطر: غياب توقيع Windows.
الأثر: تحذيرات SmartScreen وضعف الثقة.
المعالجة: اعتماد توقيع Authenticode أو حصر التوزيع داخلياً.
الأولوية: متوسطة.

الخطر: تغيير مخطط قاعدة البيانات.
الأثر: فشل تشغيل النسخة المحلية.
المعالجة: اختبار ترقية وترحيل لكل إصدار وعدم إعادة إنشاء قاعدة المستخدم.
الأولوية: عالية.

8. المخرجات النهائية المتوقعة
-------------------------------------------------------------------------------

  1. Android Protected APK:
     حزمة موقعة ومشوشة وقابلة للتفعيل، مع checksum ودليل تثبيت.

  2. Windows Protected Package:
     Portable أو Installer موقّع، مع قاعدة بيانات محلية وحارس ترخيص.

  3. Vendor License Kit:
     أداة إصدار وإجراءات داخلية خارج حزمة العميل والمستودع.

  4. Documentation Set:
     أدلة البناء والتفعيل والتحديث والاستعادة والدعم وتقارير الاختبار.

9. معيار الإطلاق Go/No-Go
-------------------------------------------------------------------------------

قرار Go يصدر فقط عند تحقق جميع الشروط التالية:

  [ ] نجاح اختبارات الترخيص والتوقيع على المنصتين.
  [ ] عدم وجود private key أو keystore أو كلمات مرور في Git أو الحزم.
  [ ] نجاح اختبار التحديث واستعادة البيانات.
  [ ] اكتمال توثيق البناء والتفعيل والدعم.
  [ ] إغلاق العيوب الحرجة والعالية.
  [ ] اكتمال مراجعة أمنية للحزم النهائية.
  [ ] وجود checksum وسجل توقيع لكل إصدار.
  [ ] اعتماد المالك النهائي للإصدار.

قرار No-Go يصدر عند وجود أي من التالي:

  - مفتاح خاص داخل المستودع أو الحزمة.
  - عدم القدرة على التحقق من توقيع الترخيص.
  - فقدان بيانات بعد التحديث أو الاستعادة.
  - عدم ثبات سلوك Offline الأساسي.
  - أخطاء حرجة أو عالية غير معالجة.
  - نقص في دليل التفعيل أو الاستعادة.
